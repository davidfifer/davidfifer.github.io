Distributed Job Scheduler

Overview

Distributed Job Scheduler is a production-style backend system that enables asynchronous job execution using a scheduler service, worker service, and shared PostgreSQL persistence layer. The project demonstrates common patterns used in distributed systems, including durable job storage, polling-based work acquisition, retry handling, failure recovery, and containerized deployment.

Jobs are submitted through a REST API and stored in PostgreSQL. The scheduler service manages job scheduling and status updates, while the worker service executes pending jobs and records execution results. The project demonstrates asynchronous job processing, persistent state management, and a microservice-style architecture using Spring Boot, PostgreSQL, and Docker.

Architecture & Design

The application follows a microservice-style architecture that separates job management from job execution responsibilities. PostgreSQL acts as the system of record, ensuring job state remains durable across service restarts and failures.

  • Scheduler Service: Exposes REST endpoints for job creation and periodically identifies runnable jobs.
  • Worker Service: Polls available work, executes jobs, and updates execution status.
  • PostgreSQL Persistence: Stores job definitions, schedules, execution attempts, timestamps, and status transitions.
  • Repository Layer: Uses Spring Data JPA for persistence and transaction management.
  • Retry Mechanism: Failed jobs are automatically rescheduled until maximum retry limits are reached.
  • Job State Machine: Jobs transition through states such as PENDING, RUNNING, SUCCESS, and FAILED.
  • Metrics Tracking: Basic execution and failure counters provide operational visibility.
  • Containerized Deployment: Docker and Docker Compose enable repeatable local environments and multi-service orchestration.

Key Features

  • REST-Based Job Submission: Create scheduled jobs through a simple HTTP API.
  • Durable Job Storage: Jobs survive application restarts because state is persisted in PostgreSQL.
  • Asynchronous Processing: Job execution occurs independently from job submission.
  • Configurable Retry Logic: Failed jobs can be retried automatically up to configured limits.
  • Status Tracking: Track job execution progress and final outcomes.
  • Health Checks: Container health endpoints support operational monitoring.
  • Metrics Collection: Execution counts and failure counts provide visibility into system behavior.
  • Docker Compose Environment: Launch the complete stack with a single command.

Usage Examples

Create a Job

curl -X POST http://localhost:8080/jobs \
  -H "Content-Type: application/json" \
  -d '{
    "payload":"Generate report"
  }'

Example response:

{
  "id": "e3d2f5d2-7a7f-41be-a7d2-1df74f35f0b5",
  "status": "PENDING"
}

Retrieve Job Status

curl http://localhost:8080/jobs/e3d2f5d2-7a7f-41be-a7d2-1df74f35f0b5

Run the Complete Stack

docker compose up --build

Services

Scheduler Service : http://localhost:8080
Worker Service    : http://localhost:8081
PostgreSQL        : localhost:5432

Engineering Challenges & Solutions

  • Job Coordination: Designed database-driven job acquisition logic that ensures workers process eligible jobs while maintaining consistent job state.
  • Fault Tolerance: Persisted job state in PostgreSQL so work is not lost during application restarts or service failures.
  • Execution Tracking: Records job attempts, status transitions, and scheduling metadata, providing the foundation for future retry and recovery capabilities.
  • State Management: Created a simple job lifecycle model with clearly defined status transitions.
  • Service Separation: Split scheduling responsibilities from execution responsibilities to improve maintainability and scalability.
  • Operational Visibility: Added health endpoints and execution metrics for basic observability.
  • Developer Experience: Used Docker Compose to eliminate local environment inconsistencies and simplify project startup.

Future Enhancements
