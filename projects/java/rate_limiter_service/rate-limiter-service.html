Rate Limiter Service

Overview

Rate Limiter Service is a production-style Java/Spring Boot microservice that enforces per‑API‑key rate limits using a token bucket algorithm. It is designed to sit in front of existing APIs or be embedded in a gateway, protecting downstream services from overload and abusive traffic while preserving burst capacity for legitimate clients. The service is fully config‑driven, thread‑safe, and exposes a simple REST endpoint for checking whether a request should be allowed, along with remaining tokens.

The project emphasizes clean architecture, concurrency correctness, and testable algorithmic behavior. It includes unit tests, Dockerization, and a documented roadmap, making it a strong portfolio piece for backend and systems‑focused roles.

Architecture & Design

The Rate Limiter Service follows a layered architecture that separates HTTP handling, business logic, algorithm implementation, and configuration. This structure keeps the core rate limiting logic independent from transport concerns and makes it easy to evolve the service with new strategies or integration points.

  • Controller Layer: Exposes a REST /check endpoint that accepts an API key and returns whether the request is allowed plus remaining tokens.
  • Service Layer: Implements rate limiting rules, loads per‑key configuration, creates token buckets lazily, and applies defaults when no explicit config exists.
  • Token Bucket Algorithm: Encapsulated in a dedicated TokenBucket class with fields for capacity, current tokens, refill rate, and last refill timestamp.
  • Thread‑Safe Store: Uses a ConcurrentHashMap‑backed TokenBucketStore to manage buckets per API key safely under concurrent access.
  • Configuration Module: A RateLimitProperties class binds to application.yml, enabling per‑key and default limits without code changes.
  • DTOs: Simple request/response DTOs keep the API contract clear and decoupled from internal models.
  • Dockerized Runtime: A Dockerfile provides a reproducible container image suitable for local testing and deployment.

Key Features

  • Token Bucket Rate Limiting: Supports bursty traffic while enforcing a steady average rate per API key.
  • Per‑Key Configuration: Allows different limits for different clients via config‑driven settings.
  • Default Limits: Applies sensible defaults when a key is not explicitly configured.
  • Thread‑Safe Concurrency: Uses concurrent data structures and careful logic to avoid race conditions.
  • Clean Layered Design: Separates controller, service, store, and algorithm for maintainability.
  • REST API: Simple /check endpoint that can be called from gateways, proxies, or other services.
  • Unit Tests: Covers token bucket behavior and service‑level logic, including timing and remaining tokens.
  • Dockerization: Containerized for consistent local and cloud deployment.
  • Phase 2 Roadmap: Documented future enhancements such as additional algorithms and observability.

Usage Examples

Check Rate Limit for an API Key

curl -X POST http://localhost:8080/api/ratelimit/check \
  -H "Content-Type: application/json" \
  -d '{"apiKey":"client-123"}'

Example JSON response:

{
  "allowed": true,
  "remainingTokens": 47
}

Example application.yml Configuration

rate-limits:
  default-limit:
    capacity: 50
    refill-rate: 5
  api-keys:
    client-123:
      capacity: 100
      refill-rate: 10

Run with Docker

# Build image
docker build -t rate-limiter .

# Run container
docker run -p 8080:8080 rate-limiter

Engineering Challenges & Solutions

  • Correct Token Bucket Logic: Implemented precise refill and consume behavior with safeguards against exceeding capacity or going negative.
  • Time‑Based Refills: Used timestamps to compute how many tokens to add since the last refill, ensuring realistic rate enforcement.
  • Concurrency Safety: Chose ConcurrentHashMap and carefully structured updates to avoid race conditions when multiple requests hit the same key.
  • Config‑Driven Design: Bound rate limit settings from application.yml into a typed properties class, keeping logic flexible and environment‑aware.
  • API Contract Clarity: Introduced DTOs so the external API remains stable even if internal models change.
  • Testability: Wrote unit tests for both the algorithm and service layer, including timing‑sensitive scenarios and edge cases.
  • Production Readiness: Added Docker support and documentation so the service can be run consistently across machines.

Future Enhancements

  • Add alternative algorithms (fixed window, sliding window, leaky bucket).
  • Add distributed store support (Redis) for multi‑instance deployments.
  • Add metrics and tracing for observability (e.g., Prometheus, OpenTelemetry).
  • Add integration tests with a sample downstream API.
